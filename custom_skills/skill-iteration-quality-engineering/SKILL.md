# Skill 迭代工程與品質驗證 Skill

> **定位**：這是一個用來終結「Prompt 輪迴」的 Skill。當使用者正在建立、修改、維護或驗證 AI Skill／Agent 指令／工具流程時，協助把模糊願望轉成可測試、可追蹤、可維護、可回滾的系統工程。

## 使用情境
- 使用者一直要求 AI 修改 Skill，但每一版都不穩定、不一致或越改越亂。
- 使用者想把一段 Prompt、工作流程、Agent 設定或工具鏈路整理成正式 Skill。
- Skill 已經可以運作，但輸出品質不穩、常出現幻覺、格式錯誤或工具呼叫錯誤。
- Skill 經過多次修改後，資料夾、工具路徑、說明文件與實際行為開始不一致。
- 需要建立 Skill 的測試標準、版本保存規則、錯誤處理格式與維護清單。

## 不適用情境
- 單次聊天式改寫，不需要長期重複使用。
- 使用者只需要臨時產出一段文字，沒有要建立可維護流程。
- 任務本身沒有可驗收標準，也不願意定義輸入、輸出、限制與測試案例。
- 涉及真實生產環境部署、權限、金流、刪除或高風險操作，但沒有人工審核者。

## 核心目標
把「幫我改好」這種模糊請求，轉成一套可執行的 Skill 迭代工程：
1. 定義可量化目標。
2. 建立參考範本與輸出格式。
3. 追蹤執行鏈路。
4. 設計可診斷錯誤訊息。
5. 用漸進式披露檢查長上下文。
6. 定期做 Skill 健康檢查。
7. 用 0/1 測試驗證品質。
8. 保存高成功率版本，避免回退困難。

## 八大原則
### 原則一：目標要像食譜，不要像減肥標語
模糊目標會迫使 AI 猜測；清楚目標會讓 AI 沿著軌道執行。

**不要這樣寫：**
```text
請幫我總結這篇文章的重點。
```
**應該這樣寫：**
```text
請提取文章中的三個核心概念，並強制以 JSON 格式輸出。
每個概念包含：
- concept_name：概念名稱
- explanation：三十字以內的解釋

請參考 references/format_example.json 的格式。
```
檢查清單：
- [ ] 有明確任務數量，例如 3 個概念、5 個標籤、10 條規則。
- [ ] 有指定輸出格式，例如 JSON、表格、清單、YAML、Markdown。
- [ ] 有提供參考範本，例如 `references/format_example.json`。
- [ ] 有說明不該做什麼，例如不要自由發揮、不要延伸推測、不要改變語氣。
- [ ] 有定義成功結果，例如可被程式解析、可直接貼進資料庫、可供業務篩選。

### 原則二：讓 AI 的思考過程像直播，不是黑盒子
AI 任務中間會做很多隱性決策：先做什麼、跳過什麼、何時重試、何時改寫、何時呼叫工具。若看不到過程，就無法知道哪一步出錯。

執行鏈路需要記錄：任務拆解步驟；每一步的輸入摘要；每一步的輸出摘要；使用了哪些工具；工具回傳了什麼；哪一步出現錯誤；哪一步開始重試；最終輸出與原目標是否一致。

靜默失敗處理：AI 常出現「API 200 OK，但內容完全錯」的靜默失敗。這時不能只靠程式錯誤碼，要用追蹤軌跡還原 AI 在哪一步想歪。

當使用者要求檢查一個 Skill 時，必須輸出：
```markdown
## 執行鏈路觀察
| 步驟 | 任務 | 輸入摘要 | 輸出摘要 | 工具 | 狀態 |
|---|---|---|---|---|---|

## 可疑節點
- 節點：
- 可疑原因：
- 建議檢查：
```

### 原則三：錯誤訊息要像醫生問診，不要只說「你生病了」
錯誤訊息必須讓 AI 或人類知道下一步該做什麼。

**不好的錯誤訊息：**
```text
Error: 429
```
**好的錯誤訊息：**
```text
[錯誤] 429 insufficient_quota
[可能原因]
1. API 餘額不足
2. 同一時間 request 過多，觸發速限
[建議下一步]
1. 開啟 API 後台確認餘額
2. 查閱官方文件確認速限設定
3. 若為速限，等待後重試或降低併發數
```
錯誤訊息模板：
```text
[錯誤類型] 
[發生位置] 
[輸入摘要] 
[可能原因] 
[建議下一步] 
[是否可自動重試] 是／否
[是否需要人工介入] 是／否
```
錯誤訊息標準：不只回傳錯誤碼；必須說明錯誤發生在哪一步；必須列出 1–3 個可能原因；必須提供下一步行動；高風險錯誤必須停止，不可硬做。

### 原則四：先看全景，再深入細節
長 session 或大型 Skill 不應一次全部展開。要先看輪廓，再展開可疑節點。

漸進式披露流程：
1. **全景掃描**：列出所有步驟、工具、錯誤、重試與輸出摘要。
2. **定位異常**：找出重試過多、輸出漂移、工具錯誤、格式破壞的節點。
3. **局部展開**：只展開異常節點的完整上下文。
4. **修正局部**：先修小區塊，不要整份 Skill 重寫。
5. **回歸測試**：確認修正沒有破壞原本可用功能。

避免 Context Rot：當上下文過長時，模型注意力會被稀釋。不要把所有內容一次丟給 AI。先摘要，再定位，再展開。

分析輸出格式：
```markdown
## 全景掃描
| 區塊 | 摘要 | 狀態 |
|---|---|---|

## 建議優先展開的區塊
1. 
2. 
3. 

## 暫不需要展開的區塊
- 
```

### 原則五：定期幫 Skill 做健康檢查
Skill 經過多次修改後，最容易出現「說明文件、工具路徑、實際行為」不一致。

| 檢查項目 | 判斷標準 |
|---|---|
| 觸發條件 | 是否明確說明何時使用與何時不用 |
| 任務邊界 | 是否定義允許與禁止範圍 |
| 輸入格式 | 是否說明需要哪些資料 |
| 輸出格式 | 是否有固定結構與範例 |
| 工具路徑 | 說明文件中的路徑是否真的存在 |
| 工具行為 | 工具實際輸出是否符合描述 |
| 錯誤處理 | 是否有可診斷錯誤訊息 |
| 測試案例 | 是否有通過／不通過標準 |
| 版本紀錄 | 是否保存可用版本 |
| 參考資料 | references/ 是否有範本與風格樣本 |

健康檢查輸出格式：
```markdown
## Skill 健康檢查報告

## 1. 結論
- 狀態：健康／需修復／不可用
- 最大風險：

## 2. 結構檢查
| 項目 | 通過 | 問題 | 修正建議 |
|---|---|---|---|

## 3. 說明與行為一致性
| 說明文件寫法 | 實際行為 | 是否一致 |
|---|---|---|

## 4. 優先修復清單
1. 
2. 
3. 
```

### 原則六：測試要用「過／不過」判定，不要用「感覺還不錯」
「看起來可以」不是測試標準。測試要能被判定為 1 或 0。

| 指標 | 通過條件 |
|---|---|
| 格式遵循度 | JSON、表格、Markdown 或指定格式可直接解析 |
| 欄位完整度 | 必填欄位全部存在 |
| 幻覺攔截 | 沒有資料時會說不知道，不會瞎編 |
| 工具呼叫準確率 | 選對工具並填對必填參數 |
| 錯誤診斷 | 錯誤訊息包含類型、原因與下一步 |
| 邊界遵守 | 沒有執行禁止任務 |
| 參考範本遵守 | 輸出風格與 references/ 範本一致 |
| 回歸穩定性 | 修正後沒有破壞原本功能 |

測試批次原則：不要只跑一次。至少跑 10 次或用 10 組案例測試。
```text
成功率 = 通過次數 / 測試總次數
9/10：可用，建議存版
7/10：不穩，需定位失敗類型
5/10 以下：結構可能有根本問題，需重設目標與流程
```
LLM-as-a-Judge 使用方式：可用另一個低成本模型作為裁判，但裁判 prompt 必須明確要求：只輸出通過或不通過；必須引用失敗證據；不可用主觀分數；不可說「大致可以」；每個測試項目都要有 0/1 結果。

### 原則七：好版本要立刻存檔
只要測到高成功率版本，立刻保存，不要等下一版再說。

保存時機：成功率達 8/10 以上；修正重大錯誤後首次穩定；新增功能前；重構資料夾或工具前；修改核心 prompt 前；上線前。

版本紀錄格式：
```markdown
## Version Log

### v0.1.0
- 狀態：
- 通過測試：
- 已知問題：
- 變更內容：
- 回滾方式：

### v0.2.0
- 狀態：
- 通過測試：
- 已知問題：
- 變更內容：
- 回滾方式：
```
命名建議：
```text
skill-name_v0.1.0_baseline
skill-name_v0.2.0_tested-8of10
skill-name_v1.0.0_stable
```

### 原則八：換新模型時先做減法，不要一直加規則
每次模型世代更新，最大的技術債不是「規則不夠」，而是**上一代為了補強弱模型而寫的規則留在原地**。新世代模型指令遵循能力更強，這些舊補強會被照字面執行，反而降低品質。

換代時的刪除清單：
| 舊補強寫法 | 新世代模型上的後果 | 處理 |
|---|---|---|
| 「輸出前逐項自我檢查」「double-check」「再確認一次」 | 與內建自我修正疊加，過度驗證、浪費 token、品質無提升 | 刪除；若是給人看的稽核痕跡則保留並改標示為人工抽查 |
| 「用 subagent 驗證」「開代理複查」 | 成本與時間倍增 | 刪除，改為明確委派門檻與數量上限 |
| 「只回報嚴重問題」「請保守」「只挑重點」 | 照字面執行，漏報真實問題 | 改成兩段式：先全量產出，再依明確規則篩選 |
| 「不要思考」「不要輸出 thinking 標籤」 | 指名反而提高標籤外洩機率（待依版本驗證） | 改成通用句「不要在回覆中包含內部或系統 XML 標籤」 |
| 沿用舊模型的參數與模式預設 | 成本與品質雙輸 | 重跑一次參數掃描再訂預設 |

關鍵判準：稽核痕跡 vs. 品質補強。驗證步驟若目的是**留下給人審核的痕跡**（合規、對外溝通把關、財務數字），保留；若目的是**提升模型輸出品質**，刪除。這一刀決定了刪對還是刪錯。

正面示範優於禁止清單：描述你要的樣子，比列舉你不要的東西有效。禁止語只在安全邊界使用，風格與格式一律改寫成正面示範。

減法的起手式：從「比你覺得安全的更少結構」開始，量測後再依實際失敗案例把規則加回來。每加回一條規則，都要能指出它修好的是哪一個具體失敗案例；指不出來就不要加。

## 標準工作流程
### Phase 1：界定任務
- 這個 Skill 要解決什麼問題？
- 使用者什麼時候會叫用它？
- 它不該處理什麼？
- 成功結果長什麼樣？
- 是否需要工具、資料夾、範本或測試集？

### Phase 2：建立 Skill 骨架
Description（何時使用）、Inputs（需要哪些資料）、Process（按順序執行哪些步驟）、Outputs（固定輸出格式）、Guardrails（禁止事項與安全邊界）、Error Handling（錯誤診斷格式）、Tests（0/1 測試案例）、Versioning（版本保存規則）。

### Phase 3：建立 references/
把使用者喜歡的範本放進 references/：
```text
references/
- format_example.json
- tone_example.md
- output_example.md
- bad_example.md
```

### Phase 4：測試
至少建立三類測試：
1. **正常案例**：輸入完整且清楚。
2. **缺資料案例**：測試是否會說不知道或要求補資料。
3. **邊界案例**：測試是否會拒絕不該做的事。

### Phase 5：觀察與修正
- 找出失敗節點。
- 只修失敗區塊，不整份重寫。
- 修正後跑回歸測試。
- 成功率達標後保存版本。

### Phase 6：維護
定期檢查文件與行為是否一致；清理失效工具路徑；更新 references/；保存穩定版本；記錄已知問題。

## 品質標準
- 不接受「看起來不錯」作為驗收。
- 不用主觀 1–5 分評分，改用 0/1 判定。
- 不整份重寫，除非原始結構完全不可用。
- 不讓工具路徑、說明文件與實際行為分離。
- 不在未保存穩定版本前做大改版。
- 不把所有內容塞進一個巨大 prompt，要拆成可維護結構。
- 不因為 AI 沒報錯就認定成功，要檢查靜默失敗。
- 不在新模型上沿用舊模型的補強指令，換代先做減法再補約束。
- 不用禁止清單處理風格與格式問題，改用正面示範。
- 不加無法對應到具體失敗案例的規則。

## 啟用提示詞
請啟用「Skill 迭代工程與品質驗證 Skill」。任務：協助我把以下 Prompt、工作流程、Agent 設定或 Skill 草稿，整理成可維護、可測試、可追蹤、可回滾的正式 Skill。請先定義食譜式目標，再建立 Skill 骨架、0/1 測試表、錯誤處理格式與版本保存規則。

## 標準執行契約

### 觸發與輸入

使用者明確要求「Skill 迭代工程與品質驗證 Skill」的核心任務，或輸入與本技能描述高度相符時才啟用。先確認目標、受眾、上下文、資料來源、授權、限制條件與希望的輸出格式；未提供的資訊不得自行補成事實。

### 執行順序

1. 盤點輸入、授權、敏感資料與可能的外部依賴，先列出缺口。
2. 依上方技能流程逐步處理，將事實、推論、假設與建議分開。
3. 產出可直接審閱的結果，列出引用、未驗證事項、風險與人工決策節點。
4. 執行輸出前檢查，確認沒有虛構證據、洩漏敏感資料或超出使用者範圍的動作。

## 輸出契約

至少提供：

- **結果或草稿**：依使用者要求產出分析、策略、腳本、內容、清單或計畫。
- **假設與限制**：明確標示資料不足、未驗證推論與適用範圍。
- **驗證紀錄**：列出使用的來源、檢查方式、驗收條件與尚待確認事項。
- **風險與下一步**：指出人工核准點、低成本驗證方式與可恢復的後續行動。

## 安全與人工核准

目前風險等級：**high**。需要人工確認。本匯入版本為 `instruction_only`，不代表已授權任何外部連接或寫入適配器。

- 先確認任務目標、輸入來源、使用授權、範圍與輸出格式；缺少關鍵資訊時先列出假設並提出最少必要問題。
- 不得捏造事實、數據、案例、評價、客戶反饋、媒體報導、認證或研究來源；無法驗證的內容必須標示為假設或待驗證。
- 只使用使用者提供或明確授權的內容；不得繞過登入、CAPTCHA、付費牆、存取控制或第三方服務限制。
- 外部服務一律採唯讀或草稿模式；發送、發佈、建立、更新、刪除、部署、交易、預算變更與權限變更前必須取得明確人工批准。
- 對個人、客戶、學生、財務、合約或私有資料採資料最小化；輸出前遮罩識別資訊，避免複製原始敏感資料。
- 涉及外部資料時記錄來源、擷取時間與查證限制；將可觀察事實、推論與建議分開呈現。
