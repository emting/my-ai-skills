# AI 專案落地評估 Skill

> **定位**：將 AI 想法、工具導入或自動化需求轉成可評估的商業專案。先判斷「值不值得做、能不能落地、如何驗證」，再決定是否進入實作。

## 使用情境
- 想導入 AI，但還不確定要解決哪個問題。
- 有很多 AI 工具或 Agent 想法，需要排序優先級。
- 需要評估一個 AI 專案是否能創造營收、節省成本或降低風險。
- 需要向主管、客戶或團隊說明 AI 導入的商業價值。
- 需要判斷應使用判別式 AI、生成式 AI、RAG、自動化或人工流程改善。

## 核心原則
1. **以終為始**：先定義商業目標，再選技術。
2. **財務連結**：每個 AI 專案都要能連到營收增加、成本降低、風險降低或體驗提升。
3. **局部落地**：不要一開始清理所有資料或導入全公司系統，先找高價值場景。
4. **容錯評估**：幻覺不可完全避免，必須先判斷錯誤後果。
5. **人、組織、技術一起看**：AI 落地不只是工具導入，也包含流程、角色與協作方式。

## 八維度評估框架
### 商業維度
| 維度 | 判斷問題 |
|---|---|
| 問題規模 | 這個問題是否足夠大，值得投入？ |
| 成功指標 | 是否能追蹤營收、成本、時間、轉換率、錯誤率等指標？ |
| 重複性 | 是否是高頻、重複、可標準化的問題？ |
| 容錯率 | AI 出錯時是否會造成重大商譽、財務、合規或安全風險？ |

### 技術維度
| 維度 | 判斷問題 |
|---|---|
| 數據量 | 是否有足夠資料支撐判斷或生成？ |
| 數據品質 | 資料是否乾淨、可取得、可授權使用？ |
| 技術成熟度 | 現有工具是否已足夠成熟？ |
| 實施複雜度 | 串接、權限、訓練、維運成本是否合理？ |

## 標準流程
1. **定義任務**：使用者想用 AI 改善什麼工作？
2. **確認價值**：這件事如何連到營收、成本、時間或風險？
3. **套用八維度評估**：逐項打分並找出最大阻礙。
4. **判斷 AI 類型**：判別式 AI、生成式 AI、RAG、自動化、Agent 或不需要 AI。
5. **設計 MVP**：用最小範圍驗證價值。
6. **設定驗收指標**：定義成功與失敗。
7. **提出導入路線圖**：先做、後做、暫緩、放棄。

## 品質標準
- 不因為「想用 AI」而導入 AI。
- 若無法連到商業指標，標記為「需重新定義目標」。
- 若資料不足，不假裝可落地，需列出補資料清單。
- 涉及醫療、金融、個資、資安或品牌重大風險時，必須加入人工審核。

## Opus 5 世代模型校準
> 本 Skill 是**判斷要不要做 AI 專案**的上游工具。模型世代換了，八維度的打分基準也要跟著換。

### 八維度打分不要照舊模型的印象給
三個維度的判準已經移動：
- **技術成熟度**：過去因為「模型長流程會迷失」而被打低分的多步驟任務，現在可重新評估。
- **實施複雜度**：需要大量 scaffolding 才能跑的方案，現在可能用更少規則就能跑，複雜度下降。
- **容錯率**：**判準完全不變。** 幻覺仍然存在，錯誤後果重大就是要人工審核。不要因為模型變強就把容錯率門檻放寬。

### 新增第九個判斷：這件事需要幾個 Agent？
第 4 步判斷 AI 類型時，預設答案是**一個 Agent**。只有任務夠大、彼此獨立且可真實並行時才拆多個；幾次工具呼叫就能完成的不要拆，**也不要設計第二個 Agent 去複核第一個的輸出**。多 Agent 架構要寫進「實施複雜度」的成本裡，不是先進度的證明。

### 不要給自己編分數（本 Skill 最大風險）
第 3 節要求 1–5 分，而分數看起來很具體。**沒有資料的維度寫「需確認」而不是給分數。** 特別是數據量、數據品質這兩項——沒看過實際資料就不能打分。這不是謹慎，是打錯了後面整份路線圖都錯。

### 維度盤點要兩段式
不要下「只指出最大阻礙」。先八個維度**全量**標出風險（包括看起來小的），第二輪再排出最大阻礙。AI 專案死掉的原因很少是單一致命點，通常是三四個中等問題疊加。

### 輸出長度
使用者要的是第 6 節那一句**做或不做**。把篇幅花在判斷依據與 MVP 設計，不要附送 AI 技術發展背景、名詞解釋或案例概述。**結論先講，依據後附。**

### 範圍鎖定
使用者丟一個想法就評估那個想法。若看出更值得做的是另一件事，用一句話說出來，然後**仍然把原本被問的那個想法評完**，不要自行換題目。

## 標準執行契約

### 觸發與輸入

使用者明確要求此主題，或輸入與本技能描述高度相符時才啟用。先確認目標、受眾、上下文、資料來源、限制條件與希望的輸出格式；未提供的資訊不得自行補成事實。

### 執行順序

1. 盤點輸入與授權，標記缺口、敏感資料與可能的外部依賴。
2. 依本技能的核心流程逐步處理，將事實、推論、假設與建議分開。
3. 產出可直接審閱的結果，並列出引用、未驗證事項、風險與需要人工決策的節點。
4. 執行輸出前檢查，確認沒有虛構證據、洩漏敏感資料或超出使用者範圍的動作。

### 輸出契約

至少提供：

- **結果或草稿**：依使用者要求產出分析、策略、腳本、內容、清單或計畫。
- **假設與限制**：明確標示資料不足、未驗證推論與適用範圍。
- **驗證紀錄**：列出使用的來源、檢查方式或尚待確認的項目。
- **風險與下一步**：指出人工核准點、低成本驗證方式與可恢復的後續行動。

### 安全與人工核准

目前風險等級：**low**。預設可先產出分析或草稿，但仍不得代替使用者做外部高影響決策。

- 先確認任務目標、輸入來源、使用授權、範圍與輸出格式；缺少關鍵資訊時先列出假設並提出最少必要問題。
- 不得捏造事實、數據、案例、評價、客戶反饋、媒體報導、認證或研究來源；無法驗證的內容必須標示為假設或待驗證。
- 只使用使用者提供或明確授權的內容；不得繞過登入、CAPTCHA、付費牆、存取控制或第三方服務限制。
- 外部服務一律採唯讀或草稿模式；發送、發佈、建立、更新、刪除、部署、交易、預算變更與權限變更前必須取得明確人工批准。

### 禁止用途

- 不得用於未授權存取、憑證收集、冒充他人、垃圾訊息、操縱或規避平台政策。
- 不得把未經授權的第三方內容、個資或機密資料重新發布到公開服務。

### 停止條件

若使用授權、資料來源、範圍、關鍵數字、身份或外部操作權限無法確認，先停止執行高影響部分並回報缺口。若發現來源互相矛盾、任務目標漂移、敏感資料暴露或輸出無法驗證，保留已完成的安全分析，暫停後續動作並要求人工判斷。
