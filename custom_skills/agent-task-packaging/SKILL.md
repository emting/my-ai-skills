# Agent 任務封包 Skill｜把模糊需求變成可委派可驗收的任務

> **定位**：任務交給 Agent 後失敗，很少是因為能力不足，通常是**進去的時候邊界就不清楚**。本 Skill 只做一件事：把一個模糊需求封裝成可委派、可驗收的任務，或判定它現在還不能交出去。
>
> **來源**：綜合 Linear 作為 Agentic Work OS（Triage-to-Agent、Agent Suitability）與個人網站實作 SOP（Task Contract、Stop Rules）兩份手冊，結論一致。

## 1. 何時啟用
- 要把一個點子、一篇長文、一個 GitHub 專案或一句需求交給 Agent 執行
- 不確定這件事該不該自己做
- 上一次交出去的結果偏掉，想知道是哪裡沒講清楚
- 要寫 issue、task prompt 或 Codex／Claude Code 的任務指令

**不適用**：已經寫清楚的任務（直接執行就好）、純粹的策略判斷、需要你本人做決定的事。

## 2. 先判定適合度（不是每件事都該委派）

| 標籤 | 意思 | 處置 |
|---|---|---|
| 🟢 Agent-ready | 目標、邊界、驗收標準都明確 | 直接封包交出去 |
| 🟡 需補上下文 | 方向對但缺資料或驗收標準 | 列出缺什麼，補齊後再交 |
| 🔵 需人類判斷 | 涉及取捨、品牌、定價、對外承諾 | 你先決定，Agent 只做執行面 |
| 🔴 不得委派 | 學生與家長個資、付款資料、投資交易、未查證的法規與資安建議、production 部署與破壞性變更 | 不交，Agent 最多整理資訊與風險 |

這一步不能略過。沒有適合度判定的任務封包，只是把錯的事情包得更好看。

## 3. 任務封包格式
```text
Outcome：一個、可驗收的成果（不是一組待辦）

Context：背景、現況、為什麼現在要做
Read first：該先看哪些檔案或頁面

Deliverables：具體交付物與格式
Acceptance Criteria：可觀察的完成條件（含錯誤與空白狀態）

Allowed scope：可以動哪些地方
Do not change：明確的禁止區與非目標

Verification：要跑哪些檢查或人工確認什麼
Stop rules：什麼情況下停下來問我，而不是繼續猜
Rollback：怎麼撤銷

Human gate：哪一步必須由我核准
```
不是每個欄位都必填。小任務只需 Outcome＋Acceptance Criteria＋Do not change 三項；**欄位數量要隨任務大小調整，不是每次都填滿**。

## 4. 寫 Acceptance Criteria 的三個原則
1. **可觀察**：寫「手機 375px 下導覽不跑版」，不寫「體驗要好」。
2. **包含失敗路徑**：正常情況之外，要寫空白、錯誤、資料不足時該怎麼表現。這是最常被漏掉的一塊。
3. **標明證據要求**：研究型任務一律要求附來源，並明訂「不得假設官方未寫明的允許用途」。

## 5. Stop Rules（寫進封包裡）
- 同一個錯誤連續兩次修不好：停手，縮小重現案例重新找根因，不要繼續試。
- 發現需要新增套件、新服務、資料庫或改架構：先問，除非能證明它阻擋了目前任務。
- 修改範圍超出原定 scope，或同時碰到三個以上核心模組：拆成下一個任務。
- 需要真實 token、真實個資或不受限網路：改用 fixture；無法替代就交回人工。
- 自動化一個流程前，它必須已經手動穩定跑過至少三次。

## 6. 執行步驟
1. 讀懂需求，用一句話講出你理解的 Outcome。如果講不出一句，這個任務本身就該拆。
2. 判定適合度標籤（第 2 節）。🔴 直接停下來告訴使用者為什麼不能委派。
3. 盤點缺失的資訊：**先全量列出你需要但沒有的東西**，再判斷哪些是真的阻擋。不要邊看邊自我審查。
4. 填寫封包（第 3 節）。不知道的欄位寫「需確認」，不要推測。
5. 建議執行者（Codex／Lovable／Hermes／n8n／你本人）並說明理由。
6. 標出 Human Gate：哪一步不能自動過。

## 7. Opus 5 世代模型校準
### 欄位不要填滿
任務封包是固定模板，這正是新世代模型最容易出問題的形式。使用者沒講的 Context、沒講的驗收標準，補上去之後看起來很專業，但 Agent 會拿這些編出來的條件當真執行。**沒有就寫「需確認」**。
### 盤點要全量，篩選才收斂
找「缺什麼上下文」時要全部列出。這是盤點型任務，不能下「只列最重要的幾個」——真正搞砸任務的常常是看起來很小的那條。全量列完再排優先序。
### 封包長度要匹配任務大小
一個改文案的任務不需要八個欄位。過度封裝本身就是一種成本，也會讓你下次懶得用。
### 不要設計「再開一個 Agent 複核」
新世代模型的自我修正已經內建。驗收要靠**客觀檢查與人工 Gate**，不是再叫一個 Agent 來看第一個 Agent。能一個做完就用一個。
### 驗收標準不能寫成「只回報嚴重問題」
如果要 Agent 做檢查或 review，要求它**全部回報**，你自己再篩。叫它「只講重要的」，新世代模型會字面執行，真的就只講很少。
### 人工 Gate 全數保留
production 部署、DNS、破壞性 migration、刪除媒體、secrets、對外發佈——這些不因為模型能力變強而放寬。模型越能自主執行，這些閘門越重要。

## 8. 交付標準（交出去前人工抽查）
- [ ] Outcome 是一個成果，不是一組待辦
- [ ] Acceptance Criteria 可觀察，且包含失敗與空白狀態
- [ ] 有明確的禁止區
- [ ] 推測的內容都標成「需確認」，沒有裝成事實
- [ ] Human Gate 已標出
- [ ] 🔴 類內容沒有被包進去

## 標準執行契約

### 觸發與輸入

使用者明確要求此主題，或輸入與本技能描述高度相符時才啟用。先確認目標、受眾、上下文、資料來源、限制條件與希望的輸出格式；未提供的資訊不得自行補成事實。

### 執行順序

1. 盤點輸入與授權，標記缺口、敏感資料與可能的外部依賴。
2. 依本技能的核心流程逐步處理，將事實、推論、假設與建議分開。
3. 產出可直接審閱的結果，並列出引用、未驗證事項、風險與需要人工決策的節點。
4. 執行輸出前檢查，確認沒有虛構證據、洩漏敏感資料或超出使用者範圍的動作。

### 輸出契約

至少提供：

- **結果或草稿**：依使用者要求產出分析、策略、腳本、內容、清單或計畫。
- **假設與限制**：明確標示資料不足、未驗證推論與適用範圍。
- **驗證紀錄**：列出使用的來源、檢查方式或尚待確認的項目。
- **風險與下一步**：指出人工核准點、低成本驗證方式與可恢復的後續行動。

### 安全與人工核准

目前風險等級：**low**。預設可先產出分析或草稿，但仍不得代替使用者做外部高影響決策。

- 先確認任務目標、輸入來源、使用授權、範圍與輸出格式；缺少關鍵資訊時先列出假設並提出最少必要問題。
- 不得捏造事實、數據、案例、評價、客戶反饋、媒體報導、認證或研究來源；無法驗證的內容必須標示為假設或待驗證。
- 只使用使用者提供或明確授權的內容；不得繞過登入、CAPTCHA、付費牆、存取控制或第三方服務限制。
- 外部服務一律採唯讀或草稿模式；發送、發佈、建立、更新、刪除、部署、交易、預算變更與權限變更前必須取得明確人工批准。

### 禁止用途

- 不得用於未授權存取、憑證收集、冒充他人、垃圾訊息、操縱或規避平台政策。
- 不得把未經授權的第三方內容、個資或機密資料重新發布到公開服務。

### 停止條件

若使用授權、資料來源、範圍、關鍵數字、身份或外部操作權限無法確認，先停止執行高影響部分並回報缺口。若發現來源互相矛盾、任務目標漂移、敏感資料暴露或輸出無法驗證，保留已完成的安全分析，暫停後續動作並要求人工判斷。
