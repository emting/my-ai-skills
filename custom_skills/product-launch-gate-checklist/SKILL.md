# 產品上線關卡檢查 Skill｜八階段 Exit Criteria

> **定位**：這不是待辦清單產生器，而是**關卡判斷器**。每次啟用只回答一個問題：以目前的狀態，這個專案能不能離開現在這一關？
> **來源**：階段拆解與 Exit Criteria 來自「產品/功能開發上線 SOP」模板頁。該頁是專案實作用的模板，本技能是判斷用的 Skill，兩者搭配使用。

## 1. 何時啟用
- 要決定某個功能能不能進入下一階段
- 上線前想知道還缺什麼，或是否該延期
- 專案卡住，想確認卡在哪一關
- 事後檢討：哪一關其實沒過就放行了

**不適用**：專案立項前的點子評估（用 `ai-project-feasibility-assessment` 或 `mvp-validation-iteration`），以及純技術除錯。

## 2. 八個關卡
| Phase | 目的 | Exit Criteria |
|---|---|---|
| 0 發想與立項 | 確認值不值得做 | 對「做什麼、為什麼」有共識；已排入 Roadmap 並有 Owner |
| 1 需求定義 | 想法轉成規格 | PRD 經 Design／Eng／QA Review 通過；時程與資源確認 |
| 2 設計 | 體驗清晰且可實作 | Design Freeze，PM ＋ Eng sign-off |
| 3 開發 | 規格轉成可運行產品 | MVP ticket 全 Done，CI 全綠，Staging 可走完主流程 |
| 4 測試 | 風險降到可接受 | 無 P0／P1，P2 以下有計畫；QA sign-off |
| 5 上線前準備 | 不因「沒想到」而失敗 | Go/No-Go 決議為 Go，相關團隊就緒 |
| 6 發佈 | 依計畫穩健推出 | 100% 放量且指標穩定 |
| 7 監控與迭代 | 驗證目標並回收學習 | 成效結論與 Stakeholder 對齊，後續 Action 已排入 |

## 3. 執行步驟
1. **定位**：確認目前在哪一關。若使用者說不清楚，用「最後一個明確達成的 Exit Criteria」往回推。
2. **逐條核對該關的 Exit Criteria**，每條標三種狀態之一：
   - ✅ 已達成（有具體證據）
   - ❌ 未達成
   - ❓ 需確認（**沒有資料就是這個，不要猜成 ✅**）
3. **給結論**：Go／No-Go／有條件 Go。有條件 Go 要寫明條件與負責人。
4. **只列阻擋項**：擋住這一關的那幾條，以及每條的最小完成動作。不要把整關的 checklist 重抄一遍。
5. **標出被跳過的前一關**：如果發現前面某關的 Exit Criteria 其實沒過，直接指出來。這通常才是真正的問題。

## 4. 輸出格式
```markdown
目前關卡：Phase X
結論：Go / No-Go / 有條件 Go

阻擋項
1. [條件] — 現況 — 最小完成動作 — 負責人

需確認（資料不足，未計入判斷）
- ...

風險提醒
- 若有前面關卡被跳過，寫在這裡
```

## 5. Opus 5 世代模型校準
### ❓ 不能被四捨五入成 ✅
這是本 Skill 唯一真正重要的規則。八關 × 每關數條 Exit Criteria 是一張固定表格，新世代模型會傾向把每一格填滿判斷。**只要沒有明確證據，就標「需確認」**，並且不計入 Go 的依據。一張全綠但有一半是推測的關卡表，會直接導致錯誤放行。

### 只列阻擋項，不要重抄清單
來源 SOP 已經有完整 checklist。Skill 的價值在於**篩掉不相關的**，只留下現在擋路的那幾條。輸出長度應該隨阻擋項數量變動，一項就寫一項。

### 盤點與判斷分兩段
找阻擋項時全量掃過該關所有條件，不要邊看邊自我篩選「這條應該不重要」。全部掃完，再依「是否擋住出關」排序。這個順序不能顛倒。

### 驗證關卡全部保留
QA sign-off、Go/No-Go 會議、Rollback 機制、安全與隱私 Review 都是**人工關卡**，不因為模型判斷過就視為完成。本 Skill 產出的是判斷建議，Go/No-Go 的決策權在人。

### 範圍鎖定
使用者問 Phase 3 能不能出關，就回答 Phase 3。不要順便重寫 PRD、補設計建議或提出架構改法。若你認為題目問錯了（例如真正的問題在 Phase 1），用一句話說明後，仍先回答被問的那一關。

## 6. 啟用提示詞
```text
請啟用「產品上線關卡檢查 Skill」。

專案：
目前我認為在：Phase X

現況：
[貼上進度、已完成項目、已知問題]

請核對該關的 Exit Criteria，給 Go／No-Go／有條件 Go，並只列出阻擋項與最小完成動作。
資料不足的條件請標「需確認」，不要當成已達成。
如果你發現前面關卡其實沒過，直接告訴我。
```

## 標準執行契約

### 觸發與輸入

使用者明確要求此主題，或輸入與本技能描述高度相符時才啟用。先確認目標、受眾、上下文、資料來源、限制條件與希望的輸出格式；未提供的資訊不得自行補成事實。

### 執行順序

1. 盤點輸入與授權，標記缺口、敏感資料與可能的外部依賴。
2. 依本技能的核心流程逐步處理，將事實、推論、假設與建議分開。
3. 產出可直接審閱的結果，並列出引用、未驗證事項、風險與需要人工決策的節點。
4. 執行輸出前檢查，確認沒有虛構證據、洩漏敏感資料或超出使用者範圍的動作。

### 輸出契約

至少提供：

- **結果或草稿**：依使用者要求產出分析、策略、腳本、內容、清單或計畫。
- **假設與限制**：明確標示資料不足、未驗證推論與適用範圍。
- **驗證紀錄**：列出使用的來源、檢查方式或尚待確認的項目。
- **風險與下一步**：指出人工核准點、低成本驗證方式與可恢復的後續行動。

### 安全與人工核准

目前風險等級：**high**。需要人工確認。

- 先確認任務目標、輸入來源、使用授權、範圍與輸出格式；缺少關鍵資訊時先列出假設並提出最少必要問題。
- 不得捏造事實、數據、案例、評價、客戶反饋、媒體報導、認證或研究來源；無法驗證的內容必須標示為假設或待驗證。
- 只使用使用者提供或明確授權的內容；不得繞過登入、CAPTCHA、付費牆、存取控制或第三方服務限制。
- 外部服務一律採唯讀或草稿模式；發送、發佈、建立、更新、刪除、部署、交易、預算變更與權限變更前必須取得明確人工批准。
- 此技能只提供分析、草稿與驗證建議，不代表法律、財務、醫療、投資或營運承諾；高風險決策須由合適的人員覆核。

### 禁止用途

- 不得用於未授權存取、憑證收集、冒充他人、垃圾訊息、操縱或規避平台政策。
- 不得把未經授權的第三方內容、個資或機密資料重新發布到公開服務。
- 不得在沒有明確批准、完整上下文與可回溯驗證的情況下執行高影響外部操作。

### 停止條件

若使用授權、資料來源、範圍、關鍵數字、身份或外部操作權限無法確認，先停止執行高影響部分並回報缺口。若發現來源互相矛盾、任務目標漂移、敏感資料暴露或輸出無法驗證，保留已完成的安全分析，暫停後續動作並要求人工判斷。
